# 포트폴리오 샘플 — 삼성전자 DS부문 AI인프라/IT인프라 직무 (Autonomous Factory)

> 이 문서는 **하나의 직무를 골라 "증명해야 할 역량 → hard-to-fake 포트폴리오"로 변환한 샘플**이다.
> 다른 직무도 같은 틀(① JD에서 역량 추출 → ② 검증 가능한 프로젝트 설계 → ③ 스토리)로 복제할 수 있다.
> 근거: [jd-reverse-mapping.md](../../docs/jd-reverse-mapping.md), [portfolio-hire-cases.md](../../docs/portfolio-hire-cases.md), [domain-knowledge-module.md](../../docs/domain-knowledge-module.md)
> 자매 샘플: [skhynix-yield-data-analysis.md](skhynix-yield-data-analysis.md) (수율 데이터분석 트랙) — 같은 구조로 비교해 읽으면 좋다.

## 0. 왜 이 직무인가 (경영정보/전산 적합도 ★★★★)
- 삼성 DS 모집전공에 **컴퓨터·산업공학 명시** → 전산은 정공법, **경영정보(MIS)도 우호적**(정보시스템 기획·DB·정보보안 거버넌스가 직결).
- 직무 정의: **Data·신기술(AI/ML)로 DS부문 IT 인프라/서비스를 설계·개발해 Autonomous Factory를 구축**. "모델을 잘 만드는 사람"이 아니라 **"데이터가 흐르는 IT 시스템을 기획·설계하는 사람"**을 뽑는다 → MIS의 "비즈니스 프로세스 + 시스템 설계" 강점이 그대로 무기.
- 변별 요소: 설비 통신(SECS/GEM)과 제조 IT 스택(MES/CIM)을 **IT 언어로 번역**할 수 있는가 + **보안 거버넌스/접근제어**를 설계에 녹였는가(삼성 우대 항목 직격).

## 1. JD에서 추출한 "증명해야 할 역량"
| # | 역량 | 출처(JD) | 증명 난이도 |
|---|------|---------|-----------|
| C1 | **데이터 분석 + 통신방식 이해** (수집→적재→처리) | 필수 | 중 |
| C2 | **시스템 요구사항 기반 SW·IT인프라 기획/설계** (아키텍처) | 필수 | 높음 |
| C3 | **C/C++/C#/Python + 알고리즘** (구현·자료구조) | 우대 | 중 |
| C4 | **SW/HW 플랫폼 프로젝트 경험** (설비·IoT 연동) | 우대 | 높음 |
| C5 | **보안 거버넌스·통신보안·표준화 데이터베이스** | 우대 | 높음(MIS 차별점) |
| C6 | **현업 요구 정의·협업·문서화** | 우대 | 높음(혼자선 증명 불가) |

> 핵심 통찰: C1·C3은 부트캠프 누구나 증명해 **변별력이 낮다**. 합격을 가르는 건 **C2(IT인프라를 "설계"했는가)·C4(설비/IoT 같은 플랫폼을 다뤘는가)·C5(보안·거버넌스를 설계에 넣었는가)** — 그래서 포트폴리오는 "모델"이 아니라 **"흐르고·관제되고·통제되는 IT 시스템"**에 hard-to-fake 신호를 집중한다. MIS 전공자는 특히 C5에서 전산 전공자와 차별화된다.

## 2. 포트폴리오 설계 — "설비 데이터 수집→실시간 모니터링 IT 인프라 + 데이터 거버넌스/접근제어"

### 2.1 프로젝트 한 줄 정의
> 공개 제조/IoT 센서 데이터로 **설비 데이터를 수집(SECS/GEM 모사)→스트리밍 파이프라인으로 적재→이상 탐지→실시간 모니터링 대시보드까지 잇는 IT 인프라**를 설계·배포하고, 그 위에 **역할 기반 접근제어(RBAC)와 데이터 카탈로그(거버넌스)**를 얹어 "Autonomous Factory의 한 조각"을 직접 만든다.

- **왜 hard-to-fake한가**: "분류 모델 정확도 0.9"가 아니라 **아키텍처 다이어그램 + 동작하는 파이프라인 + 운영 지표(처리량/지연/장애복구) + 접근제어 정책**을 한 줄로 엮으면 "토이 노트북"과 명확히 구분된다. 면접관이 보고 싶은 건 "이 사람이 **시스템을 설계·운영**할 수 있는가"다.
- **데이터셋**: SECOM(UCI, 590센서×1567 반도체 공정 계측) 또는 NASA CMAPSS(설비 RUL), Bosch Production Line(Kaggle) 같은 **실제/공개 제조 데이터** + 센서 스트림은 이를 시계열로 재생(replay)해 "실시간"을 모사. 진짜 제조 계측 데이터라는 점이 도메인 신호.

### 2.2 역량 커버리지 매핑
| 역량 | 이 프로젝트에서 어떻게 증명되나 |
|------|------------------------------|
| C1 데이터+통신 | 센서 스트림을 Kafka/MQTT로 수집, **SECS/GEM의 메시지 패턴을 모사**한 수집 어댑터, 적재(Parquet/시계열DB) |
| C2 IT인프라 설계 | 3계층(수집-처리-서빙) 아키텍처 문서, Docker Compose/IaC로 재현 가능한 인프라, 모니터링(Grafana) |
| C3 코딩+알고리즘 | Python(수집/처리), 이상탐지 로직, 필요 시 C/C++로 수집 어댑터 1개 구현(삼성 코딩 신호) |
| C4 SW/HW 플랫폼 | IoT 센서 또는 가상 설비(simulator)→엣지 수집→클라우드 적재의 end-to-end 플랫폼 |
| C5 보안·거버넌스 | **RBAC 접근제어, 데이터 마스킹, 데이터 카탈로그/리니지, 감사로그** — MIS 전공자의 결정타 |
| C6 협업·문서화 | (보강책 ↓) 2인 협업 + 요구사항 명세서·ADR(아키텍처 결정기록) 문서화 |

### 2.3 hard-to-fake 4신호 심기 (2026 시장 핵심)
2026년엔 "deploy된 앱"만으론 부족하다. 다음을 의도적으로 심는다:
1. **협업 커밋** — 동료 1명과 페어(예: 한 명은 파이프라인, 한 명은 대시보드/보안)로 진행하거나 기존 데이터 엔지니어링 OSS에 PR 1건 → 타인 이름이 git에 남게.
2. **살아있는 배포 + 운영 흔적** — 클라우드(또는 무료 티어)에 배포, README에 아키텍처 다이어그램·환경변수·재현 방법·**관측 지표(throughput/latency)** 캡처.
3. **개발자다운 git 히스토리** — atomic 커밋, 브랜치/PR/머지, ADR 문서. "initial commit에 5천 줄" 금지.
4. **레퍼런스/리뷰** — 스터디·부트캠프 멘토에게 아키텍처·보안 설계 리뷰를 받은 흔적(PR 코멘트/리뷰 이슈).

> MIS 추가 신호: **데이터 거버넌스 문서**(데이터 카탈로그, 분류등급, 접근정책 매트릭스)는 전산 전공자가 잘 안 만드는 산출물 → "정보시스템을 기획하는 사람"이라는 정체성을 증명한다.

### 2.4 4주 빌드 플랜
| 주차 | 산출물 |
|------|--------|
| 1주 | 공개 데이터 선정·EDA, **요구사항 명세 + 아키텍처 다이어그램(ADR #1)**, 수집 어댑터(SECS/GEM 메시지 모사) |
| 2주 | 스트리밍 파이프라인(Kafka/MQTT→처리→시계열DB), 처리량/지연 측정, Docker Compose로 재현화 |
| 3주 | 이상탐지 로직 + **실시간 모니터링 대시보드(Grafana/Streamlit)**, 알림(threshold/drift) |
| 4주 | **보안·거버넌스 레이어**(RBAC·마스킹·감사로그·데이터 카탈로그) + 배포 + README/디자인독 + 30초 데모 영상 |

### 2.5 절대 하지 말 것 (Not 일관 / 윤리 가드레일)
- ❌ 운영 지표(throughput·latency·복구시간) **수치 조작**("hiring managers can smell fake numbers") — 측정 스크립트와 raw 로그를 함께 공개해 검증 가능하게.
- ❌ AI가 통째로 짠 인프라 코드를 이해 없이 붙여넣기 → "왜 Kafka? 왜 RBAC를 이렇게?" 후속질문에서 붕괴. **모든 아키텍처 결정은 ADR로 직접 근거를 남긴다.**
- ❌ 실데이터 없이 가짜 시나리오만 — 반드시 공개 실데이터(SECOM/CMAPSS/Bosch 등) 사용.
- ❌ 실제 삼성/타사 내부 데이터·사내 시스템 정보 사칭 또는 NDA 자료 활용 → 공개 데이터·자작 시뮬레이터만 사용한다.
- ❌ 보안 기능을 "넣었다"고 적기만 하고 동작 안 함 → 접근거부·마스킹이 실제로 작동하는 데모를 남긴다.

## 3. 스토리 — 자소서·면접 직무직결 (STAR + 5단계 프레임)

### 3.1 자소서 4번(직무 전문지식) 불릿 (Action+scope+tool+metric+outcome+proof)
> "SECOM 590센서 공정 계측 데이터를 **설비 통신(SECS/GEM) 패턴을 모사한 수집 어댑터→Kafka 스트리밍→시계열DB 적재→실시간 이상탐지 대시보드**로 잇는 IT 인프라를 설계·배포했습니다(처리량 X msg/s, 평균 지연 Y ms). 그 위에 **역할 기반 접근제어와 데이터 카탈로그(거버넌스)**를 얹어 '누가 어떤 데이터에 접근하는지 통제'까지 다뤘습니다. [GitHub/데모/아키텍처 다이어그램 링크]"

### 3.2 면접 예상 질문 → 답 뼈대 (Issue→Root Cause→Hypothesis→Test→Result)
- "왜 이 프로젝트를?" → Autonomous Factory는 "데이터가 끊김 없이 흐르고 통제되는 IT 인프라"가 전제 → 모델보다 **파이프라인·거버넌스**가 병목이라 봄(모듈 0·3).
- "왜 Kafka/MQTT를?" → 설비 데이터는 고빈도·연속 스트림 → 메시지 큐로 backpressure·재처리 보장. ADR로 대안(직접 DB insert) 대비 근거 제시.
- "SECS/GEM이 뭔가?" → SEMI 표준 설비 통신 프로토콜, 설비↔호스트 메시지 규약 → "실 설비는 이 위에서 동작, 내 어댑터는 그 메시지 패턴을 모사"(모듈 3.3, **비전공 차별점**).
- "보안은 어떻게 설계했나?" → **데이터 분류등급→접근정책 매트릭스→RBAC·마스킹·감사로그**. MIS의 정보보안 거버넌스 관점으로 답(삼성 우대 직격). **모르는 부분은 솔직히 + 논리적 접근 제시.**
- "실무 데이터는 더 다르다" → Large P/Small N, process drift, 멀티소스 통합·추적성(genealogy) 언급(모듈 4)으로 도메인 이해 입증.

### 3.3 C6(협업) 보강 멘트
> "혼자 만든 게 아니라 OO와 페어로 **파이프라인 담당/대시보드·보안 담당**을 나눠 진행하며, 데이터 스키마 변경이 하류 대시보드를 깨뜨린 충돌을 ADR과 PR 리뷰로 합의해 해결했습니다." → 면접관이 보고 싶어 하는 "요구 정의·압박 속 협업" 신호.

### 3.4 MIS 전공자 차별화 각도 (전산 전공자 대비)
> "저는 모델 성능 경쟁보다 **비즈니스 프로세스(설비 운영)→데이터 흐름→시스템 요구사항→접근통제**로 내려가는 설계를 강점으로 봅니다. 그래서 이 프로젝트도 '정확도'가 아니라 '**누가·언제·어떤 데이터를 신뢰할 수 있게 받는가**'를 중심에 뒀습니다." → 삼성 AI/IT인프라가 원하는 "정보시스템 기획자"상과 정확히 일치.

## 4. 이 샘플을 다른 직무로 복제하는 법
1. **JD 1~3개** 수집 → 1번 표처럼 역량 추출, **변별력 낮은 역량 vs 가르는 역량** 구분.
2. 가르는 역량(여기선 설계·플랫폼·거버넌스)에 **hard-to-fake 프로젝트** 1개 집중 설계(실데이터+운영지표+배포+도메인+협업).
3. 2.3의 **4신호**를 의도적으로 심기 + (MIS면) 거버넌스 산출물로 추가 차별화.
4. 3번처럼 STAR + 5단계 프레임으로 스토리화하고, **자소서 4번·영어회화·GSAT 공통 게이트**를 별도 트랙으로 병행.

> 다음 후보 직무: 삼성 SW개발(SW역량테스트 트랙), 삼성 생산관리/SCM(CIM·BI), NVIDIA IT/Infra NCG. 각각 JD 매핑 → 같은 틀 적용.
