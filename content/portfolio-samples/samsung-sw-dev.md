# 포트폴리오 샘플 — 삼성전자 DS부문 SW개발(제조&기술담당)

> 이 문서는 **하나의 직무를 골라 "증명해야 할 역량 → hard-to-fake 포트폴리오"로 변환한 샘플**이다.
> 다른 직무도 같은 틀(① JD에서 역량 추출 → ② 검증 가능한 프로젝트 설계 → ③ 스토리)로 복제할 수 있다.
> 근거: [[../../docs/jd-reverse-mapping.md]], [[../../docs/portfolio-hire-cases.md]], [[../../docs/domain-knowledge-module.md]]

## 0. 왜 이 직무인가 (전산/CS 적합도 ★★★★★)
- 삼성 DS부문 직무 중 **전산/CS 전공자 최우선 타깃**(JD 역매핑 ★★★). 모집 트랙이 SW개발이라 CS 역량이 곧 직무 적합도.
- **GSAT 대신 SW역량테스트**(C/C++/Java/Python 2문제·240분) 트랙 → "코딩으로 실력을 증명"하는 구조라 비전공자도 **코테+포트폴리오로 정공법 진입**(탐구2 사례 A: 초등교사 4년→SSAFY→삼성 SW개발).
- 단, 일반 웹/앱 SW와 다른 **제조 도메인(Smart Factory·설비제어·Edge)**을 아는 것이 변별 요소. 그냥 "잘하는 개발자"가 아니라 "제조 데이터를 다룰 줄 아는 개발자"여야 한다.

## 2. 포트폴리오 설계 — "설비 센서 시계열 이상탐지 + 실시간 처리 파이프라인 (Edge→Stream→Alert)"

### 2.1 프로젝트 한 줄 정의
> 반도체 설비 센서를 본뜬 **공개 시계열 데이터(SECOM / NASA 베어링)**로 **온라인 이상탐지 모델**을 만들고, 이를 **Kafka/MQTT 기반 실시간 스트림 파이프라인**에 얹어 **"센싱→분석→경보(Control 신호)"**까지 도는 시스템을 배포한다. 모델은 **Edge(라즈베리파이/경량 컨테이너)**에서 추론하고, **임계 초과 시 설비정지 신호(mock SECS/GEM 메시지)**를 발행한다.

- **왜 hard-to-fake한가**: 단순 "Jupyter 노트북 ML"이 아니라 ① 실제 반도체/설비 도메인 데이터 + ② 이상탐지 모델 성능 수치 + ③ **돌아가는 실시간 시스템(latency·throughput 측정)** + ④ Edge 배포 + ⑤ 도메인 해석(이상↔설비 이상 원인)을 한 줄로 엮어야 재현되므로, "코드 한 덩어리 붙여넣기"와 명확히 구분된다. SW개발 직무가 보고 싶어 하는 "코딩+시스템" 신호가 정면으로 드러난다.
- **데이터셋**:
  - **SECOM** (UCI, 1,567개 반도체 공정 계측 × 590 센서피처, pass/fail 라벨) — 진짜 반도체 공정 계측 데이터. Large P/Small N·결측·불균형이 그대로라 도메인 신호가 강함.
  - **NASA IMS Bearing / CWRU Bearing** — 설비 회전체 진동 시계열. "정상→열화→고장"이 시간축으로 들어 있어 **온라인 이상탐지·예지보전(PdM)** 데모에 적합.
  - (택1 또는 병행: SECOM=공정 계측 정적, Bearing=설비 시계열 동적. 시계열·실시간을 보여주려면 Bearing 권장, 반도체 도메인 직결성은 SECOM이 강함.)

### 2.2 역량 커버리지 매핑
| 역량 | 이 프로젝트에서 어떻게 증명되나 |
|------|------------------------------|
| C1 코딩/알고리즘 | Python(전처리·모델) + **C/C++로 Edge 추론 경량화**(슬라이딩 윈도우·온라인 통계). 코테는 별도지만 C++ 사용 흔적으로 "언어 다룸"을 보강 |
| C2 이상탐지 ML | Isolation Forest/One-Class SVM/Autoencoder 비교, PR-AUC·recall@FPR, 불균형 처리. **라벨 거의 없는 상황**(현실적)을 비지도/반지도로 |
| C3 실시간 파이프라인 | MQTT/Kafka로 센서 스트림 → 윈도우 집계 → 온라인 추론 → 경보. **p99 latency·throughput 수치** |
| C4 임베디드/Linux/제어 | 라즈베리파이(또는 Docker 경량 컨테이너) 배포, systemd 서비스화, **mock SECS/GEM(설비정지 신호) 발행** |
| C5 설계·테스트·협업 | 아키텍처 다이어그램·인터페이스 설계, **pytest + CI(GitHub Actions)**, 임계치 회귀 테스트 → CSTS/ISTQB 언어로 서술 |
| C6 제조 도메인 | 이상치를 **FDC(Fault Detection & Classification)·예지보전 관점**으로 해석(모듈3.4/4.3), "수율=이익"과 연결(모듈0) |

### 2.3 hard-to-fake 4신호 심기 (2026 시장 핵심)
2026년엔 "deploy된 앱"만으론 부족하다. 다음을 의도적으로 심는다:
1. **협업 커밋** — 동료 1명과 페어로(예: 한 명은 모델, 한 명은 스트림 인프라) 진행하거나, 기존 이상탐지/MQTT 오픈소스에 PR 1건 기여 → 타인 이름이 git에 남게. SW개발 직무는 특히 "혼자 짠 코드"보다 **인터페이스를 나눠 협업한 흔적**을 본다.
2. **살아있는 배포 + 운영 흔적** — Edge(라즈베리파이/HF Spaces/소형 VM)에 실제 가동, **대시보드(Grafana/Streamlit)에 latency·이상 알람 로그**, README에 재현 절차·환경변수·아키텍처 다이어그램.
3. **개발자다운 git 히스토리** — atomic 커밋, feature 브랜치/PR 머지, **CI 통과 뱃지**. "initial commit에 5천 줄" 금지.
4. **레퍼런스/리뷰** — 스터디·SSAFY·부트캠프 멘토 코드리뷰 흔적(PR 코멘트), **테스트 커버리지 리포트**로 품질 신호.

### 2.4 4주 빌드 플랜
| 주차 | 산출물 |
|------|--------|
| 1주 | 데이터 EDA(SECOM 불균형·결측 / Bearing 열화 구간 라벨링), 베이스라인(임계치 룰 + Isolation Forest), PR-AUC·recall 측정 |
| 2주 | **온라인 이상탐지** — 슬라이딩 윈도우 특징(RMS·kurtosis·spectral), Autoencoder/OC-SVM 비교, 오탐(false alarm)율 튜닝 + 오류분석 |
| 3주 | **실시간 파이프라인** — MQTT/Kafka 센서 스트림, 윈도우 집계, **C/C++ 경량 추론** Edge 배포, mock SECS/GEM 경보 신호, p99 latency 측정 |
| 4주 | **테스트·CI·배포 마감** — pytest+GitHub Actions, Grafana/Streamlit 대시보드, README/아키텍처 다이어그램/설계독 + 30초 데모 영상 |

### 2.5 절대 하지 말 것 (Not 일관)
- ❌ 성능 수치 조작("hiring managers can smell fake numbers"). PR-AUC·latency는 **재현 스크립트로 누구나 확인 가능**하게.
- ❌ **AI가 통째로 짠 코드를 이해 없이 붙여넣기** → "이 Autoencoder의 병목은 왜 인코더입니까?" "MQTT QoS 1과 2 중 왜 1?" 같은 후속질문에서 붕괴. AI는 보일러플레이트·리뷰에만 쓰고 **핵심 로직은 직접 설계·디버깅**.
- ❌ 실데이터 없이 `np.random`으로 만든 가짜 센서값만 — 반드시 SECOM/Bearing 같은 **공개 실데이터**를 1차 신호로.
- ❌ "실시간"이라 써놓고 배치 1회만 도는 것 — **스트림이 실제로 흐르고 latency가 측정**돼야 C3가 증명됨.

## 3. 스토리 — 자소서·면접 직무직결 (STAR + 5단계 프레임)

### 3.1 자소서 4번(직무 전문지식) 불릿 (Action+scope+tool+metric+outcome+proof)
> "설비 진동 시계열(NASA IMS Bearing)을 **슬라이딩 윈도우 특징 + Autoencoder로 온라인 이상탐지**(recall 0.9X @ 오탐 5%↓)하고, 이를 **MQTT 실시간 파이프라인(p99 latency 약 XX ms)**에 얹어 임계 초과 시 **설비정지 mock SECS/GEM 신호를 발행하는 Edge 시스템**으로 배포했습니다. 추론은 라즈베리파이에서 C++로 경량화했고, pytest+GitHub Actions CI로 품질을 보장했습니다. [GitHub/데모/대시보드 링크]"

### 3.2 면접 예상 질문 → 답 뼈대 (Issue→Root Cause→Hypothesis→Test→Result)
- "왜 이 프로젝트를?" → 설비 다운타임=수율·원가 직결(모듈0), **Sensing-Analytics-Control**이 삼성 SW개발 업무 그 자체라서.
- "라벨이 거의 없는데 어떻게 이상탐지?" → 정상 구간만으로 학습하는 **비지도(Autoencoder 재구성오차)/반지도** 선택 근거 → recall@FPR로 검증.
- "왜 Kafka가 아니라 MQTT?(또는 반대)" → 처리량·QoS·Edge 제약 트레이드오프로 답. **선택의 이유를 시스템 관점**으로.
- "C++ 경량화는 실제로 뭘 했나?" → 슬라이딩 윈도우 통계 O(1) 갱신, 메모리 풋프린트, 추론 latency 비교 수치. **하드웨어/메모리와의 상호작용을 설명**(엔비디아 시그널과 동일 결).
- "실무 설비 데이터는 더 다르다" → 멀티소스 통합·process drift·SECS/GEM 표준·FDC(모듈3.3/4.4) 언급으로 도메인 이해 입증. **모르면 솔직히 + 논리적 접근 제시**.

### 3.3 C5(협업·품질) 보강 멘트
> "혼자 만든 게 아니라 OO와 **모델/인프라로 인터페이스를 나눠** 진행하며 PR 리뷰를 주고받았고, 스트림 메시지 스키마를 두고 [구체 충돌·결정]을 겪었습니다. 테스트는 임계치 회귀 케이스를 pytest로 묶어 CI에서 강제했습니다." → 면접관이 보고 싶어 하는 "압박 속 협업 + 코드품질" 신호(CSTS/ISTQB 언어와 연결).

## 4. 이 샘플을 다른 직무로 복제하는 법
1. **JD 1~3개** 수집 → 1번 표처럼 역량 추출, **코테/시험이 직접 검증하는 역량(변별력 낮음) vs 포트폴리오로 가르는 역량** 구분.
2. 가르는 역량에 **hard-to-fake 프로젝트** 1개 집중 설계(실데이터+성능+**돌아가는 시스템/배포**+도메인 해석+협업).
3. 2.3의 **4신호**를 의도적으로 심기. SW개발 직무는 특히 **CI·테스트·인터페이스 협업** 흔적이 강한 신호.
4. 3번처럼 STAR + 5단계 프레임으로 스토리화하되, **자소서 4번(직무 전문지식)**에 정조준.
