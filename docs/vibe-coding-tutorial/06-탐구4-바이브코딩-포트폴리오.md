# 챕터 6: 탐구 4 — 바이브 코딩 포트폴리오의 현실

> **소요**: 약 16분 (3개 에이전트 동시)
> **리서치 투입**: 병렬 에이전트 3기
> **핵심 인사이트**: 명제를 더 날카롭게 좁히면 새 조사가 필요하다. 그리고 **2026년엔 "배포된 앱"조차 신호가 죽었다** — 살아남는 신호가 따로 있다.

## Context
여기서 사용자가 프로젝트의 명제를 한 단계 더 날카롭게 다듬었다. 막연한 "포트폴리오"가 아니라 구체적인 방향으로.

## The Prompt
```
조사결과 얻어진 인사이트를 정리하자면 반도체 관련 학과를 졸업하지 않고도
전산학과/경영정보학과를 졸업한 취준생이 바이브 코딩에 기반한 데이터 사이언스
능력으로 반도체 기업에 취업하는 것을 목표로 하는거야. 오픈소스와 오픈된
데이터셋을 이용해서 공정을 개선하거나 불량 탐지등 반도체 기업들이 관심을
가질만한 프로젝트를 포트폴리오로 준비하고 싶어. 먼저 이를 위한 조사를 진행해
```

## What Happened
3개 에이전트 동시:
1. **오픈 데이터셋 카탈로그** — Kaggle·UCI·HuggingFace 탐색
2. **오픈소스 생태계** — GitHub API로 스타·활성도 검증
3. **기업 관심 프로젝트 + 바이브 코딩 실현성** — 어떤 프로젝트가 가치 있고 비전공자가 만들 수 있는지

## The Result
**데이터 확보**: WM-811K(CC0, 웨이퍼맵 81만장), SECOM(공정센서) 등 반도체 직결 공개 데이터.

**오픈소스 협업 경로**: Anomalib(Intel)·RAPIDS(NVIDIA)·secsgem에 PR → "타인 이름 박힌 커밋" 만들기.

## 🔧 Debugging: "2026년의 함정"
**증상**: 조사 결과, 바이브 코딩으로 만든 "캐글 따라하기 + 배포된 앱 + 정확도 99%"는 **채용 신호가 거의 없음**.
**근본 원인**: AI로 누구나 그런 앱을 만들 수 있게 되면서 신호가 "table stakes(기본값)"로 전락. *"proof of work가 proof of prompt로 바뀌었다."*
**해결**: 살아남는 **5가지 신호**로 전환 — ① 지저분한 실데이터 처리 ② **도메인 해석**(WBM 패턴↔공정 원인) ③ 정량 성과 ④ 의사결정 기록(ADR) ⑤ 협업·공개 리더보드·유지보수.
**교훈**: 바이브 코딩의 최대 함정은 "빨리 만들 수 있어서 누구나 만든다"는 것. 차별점은 **속도가 아니라 도메인 해석과 검증**이다.

## Lessons Learned
- **명제를 날카롭게 좁히면 그만큼 조사가 정밀해진다.** "포트폴리오"→"오픈소스+오픈데이터로 불량탐지"로 좁히니 구체적 데이터셋·도구가 나왔다.
- 바이브 코딩을 **숨기지 말고 신호로 전환**하라: "무엇을 AI에 지시하고 무엇을 내가 검증했나"를 문서화하면 그게 현대 엔지니어링 역량이다.
- "3개를 얕게 < 1~2개를 깊게."

```
(1) 쓸 수 있는 공개 데이터셋 (2) 활용/기여할 오픈소스 (3) 기업이 관심 가질

```
